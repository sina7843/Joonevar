# Runbook — راه‌اندازی، پیکربندی، پشتیبان‌گیری و بازگشت

این سند برای کسی است که سامانه را اجرا و نگهداری می‌کند. هر فرمان دقیقاً همان چیزی است که اجرا شده و نتیجه‌اش دیده شده است.

## ۱. پیش‌نیازها

| مورد | نسخه |
|---|---|
| Node.js | ≥ 22.6.0 (تست‌ها و اجرای TypeScript بدون ترنسپایل به همین وابسته‌اند) |
| PostgreSQL | ۱۶ |
| Docker | فقط برای دیتابیس محلی؛ برای اجرای برنامه لازم نیست |

## ۲. راه‌اندازی از یک Checkout تمیز

```bash
git clone <repository> hamzist && cd hamzist
cp .env.example .env            # مقدارها را طبق بخش ۳ پر کنید
npm ci                          # نصب دقیقاً از package-lock.json
docker compose up -d            # دیتابیس محلی روی پورت 5433
npm run db:migrate              # اعمال migrationها
npm run db:seed                 # داده مرجع پایه و کلیدهای تنظیمات
npm run build                   # ساخت نسخه production
npm run start                   # اجرا روی پورت 3000
```

برای توسعه: `npm run dev`.

بررسی سلامت پس از اجرا:

```bash
curl -s http://127.0.0.1:3000/api/health | head -40
```

پاسخ `degraded` تا زمانی که تعرفه‌ها و مشخصات مرکز ژنتیک وارد نشده‌اند طبیعی و صادقانه است؛ `ok` فقط وقتی است که چیزی «تعیین‌نشده» نمانده باشد.

## ۳. قرارداد پیکربندی

`src/config/env.ts` هنگام بالا آمدن اعتبارسنجی می‌کند و در صورت نبود مقدار لازم **بالا نمی‌آید**.

| متغیر | لازم | توضیح |
|---|---|---|
| `APP_ENV` | بله | `development` \| `test` \| `production` |
| `INTEGRATION_MODE` | بله | `local` \| `sandbox` \| `live` — مقدار `local` در production رد می‌شود |
| `DATABASE_URL` | بله | رشته اتصال PostgreSQL |
| `PRIVATE_STORAGE_DIR` | بله | مسیر فایل‌های خصوصی، بیرون از مسیر عمومی |
| `SESSION_SECRET` | فقط در production | حداقل ۳۲ کاراکتر، از Secret Manager |
| `SITE_URL` | فقط در production | مبدأ عمومی سایت با `https` (بدون مسیر)؛ canonical، sitemap و OpenGraph از آن ساخته می‌شوند. بیرون از production مقدار خالی یعنی `http://localhost:3111` |

قواعدی که در همین اعتبارسنجی اجرا می‌شوند:

- `APP_ENV=production` با `INTEGRATION_MODE=local` **رد می‌شود**؛ production هرگز آداپتور توسعه را اجرا نمی‌کند.
- در production بدون `SESSION_SECRET` بالا نمی‌آید.
- در production بدون `SITE_URL` یا با `SITE_URL` غیر `https` بالا نمی‌آید (DEC-0150).
- درخواست آداپتور پیامک یا درگاه در production بدون Provider واقعی، خطای صریح `NOT_CONFIGURED` می‌دهد — نه پیامک بی‌صدا و نه پرداخت ساختگی.

## ۴. فعال‌سازی Provider واقعی

انتخاب سرویس هر آداپتور از `/admin/settings` گروه «یکپارچه‌سازی‌ها» انجام می‌شود و فقط سوپرادمین اجازه دارد (DEC-0122). وضعیت نصب‌شده:

| آداپتور | حالت محلی | برای واقعی‌شدن چه لازم است |
|---|---|---|
| `sms-otp` | `MOCK_AUTO` — پیامک به شماره واقعی نمی‌رود، متن در `/dev/sms` دیده می‌شود | حالت `PROVIDER` + نام و کلید سرویس |
| `payment-gateway` | `MOCK_AUTO` — بازگشت فوری و تأیید سمت سرور با همان مبلغ منجمدشده | حالت `PROVIDER` + نام و کلید درگاه |
| `map-provider` | `neshan` بدون کلید | فقط `integration.map.api_key` |
| `document-render` | `CHROMIUM` محلی، بدون سرویس بیرونی | قالب رسمی چاپی انجمن (داده، نه پیکربندی) |
| `chip-reader` | `KEYBOARD_WEDGE` — دستگاه بلوتوثی مثل صفحه‌کلید تایپ می‌کند | چیزی لازم نیست؛ یکپارچه‌سازی سخت‌افزاری حذف شد (DEC-0126) |

در `APP_ENV=production` هیچ Mock ای مؤثر نمی‌شود، حتی اگر در دیتابیس انتخاب شده باشد.

ترتیب کار برای هر آداپتور:

1. مقدار پیکربندی Provider را در محیط (نه در مخزن) یا در همان گروه تنظیمات قرار دهید؛ کلیدها در Audit و لاگ ثبت نمی‌شوند.
2. `INTEGRATION_MODE` را روی `sandbox` بگذارید و یک تراکنش/ارسال واقعی sandbox انجام دهید.
3. شاهد آن اجرا (شناسه تراکنش، پاسخ Provider، زمان) را در `docs/reports/` ثبت کنید. تا وجود این شاهد، وضعیت آداپتور `SANDBOX_VERIFIED` **ادعا نمی‌شود**.
4. فقط پس از آن `INTEGRATION_MODE=live` و همان مراحل با شاهد زنده.

`/api/health` و `/admin` وضعیت هر آداپتور را از روی پیکربندی گزارش می‌کنند؛ «تأییدشده» از روی وجود نام Provider استنتاج نمی‌شود.

## ۵. مهاجرت‌ها

```bash
npm run db:migrate     # اعمال؛ اجرای دوباره no-op است
npm run db:generate    # فقط هنگام تغییر schema، برای تولید migration جدید
```

- Drizzle در `drizzle.__drizzle_migrations` ثبت می‌کند، پس اجرای دوباره چیزی را replay نمی‌کند.
- **بازگشت (rollback):** migration معکوس خودکار وجود ندارد. مسیر امن بازگشت، بازگرداندن آخرین Snapshot است (بخش ۶) و سپس اجرای نسخه کد متناظر همان Snapshot.
- اگر یک migration در میانه شکست بخورد: نسخه کد را برنگردانید تا وضعیت دیتابیس روشن شود؛ ابتدا Snapshot را بازگردانید، سپس علت شکست را برطرف و دوباره اجرا کنید.

## ۶. پشتیبان‌گیری و بازگرداندن

دیتابیس و فایل‌های خصوصی **با هم** پشتیبان گرفته می‌شوند. یکی بدون دیگری قابل استفاده نیست: ردیف سند به کلید فایل اشاره می‌کند و فایل بدون ردیف، یتیم است.

```bash
# پشتیبان‌گیری
node tools/backup.mjs --out backups \
  --database-url "$DATABASE_URL" --storage "$PRIVATE_STORAGE_DIR"

# بازگرداندن
node tools/restore.mjs --from backups/<timestamp> \
  --database-url "$DATABASE_URL" --storage "$PRIVATE_STORAGE_DIR"
```

- هر Snapshot شامل `database.sql`، پوشه `files/` و `manifest.json` با sha256 هر فایل و خود dump است.
- بازگرداندن **قبل از نوشتن** digestها را بررسی می‌کند؛ Snapshot دستکاری‌شده اصلاً اعمال نمی‌شود.
- اگر کد جدیدتر از Snapshot است، پس از بازگرداندن `npm run db:migrate` را اجرا کنید.
- ابزار ابتدا `pg_dump`/`psql` روی PATH را امتحان می‌کند و در نبود آن‌ها از همان باینری داخل کانتینر محلی استفاده می‌کند.

این مسیر با داده یک‌بارمصرف واقعاً آزمایش شده است: `tests/db/backup-restore.test.ts` داده را می‌سازد، Snapshot می‌گیرد، schema و فایل‌ها را واقعاً حذف می‌کند، بازمی‌گرداند و بررسی می‌کند که نمونه، سند و فایل خصوصی همچنان به هم وصل‌اند.

## ۷. پایش و حریم داده

- `/api/health` — دسترسی دیتابیس، تعداد migration، کلیدهای تعیین‌نشده و وضعیت هر آداپتور. کد ۵۰۳ فقط وقتی است که دیتابیس در دسترس نباشد.
- `/admin/audit` — رویدادهای عملیاتی، فقط‌خواندنی.
- در لاگ و Audit، مقادیر حساس در **زمان نوشتن** حذف می‌شوند: `otp`, `code`, `token`, `secret`, `password`, `nationalId`, `cardNumber` و هم‌خانواده‌های آن‌ها.
- فایل‌های خصوصی هرگز مستقیم سرو نمی‌شوند؛ خواندن آن‌ها از مسیر سرور و با بررسی مالکیت/نقش انجام می‌شود.
- جدول `dev_outbound_sms` فقط در محیط توسعه پر می‌شود و در production اصلاً نوشته نمی‌شود.

## ۸. کارهایی که این بسته اجازه‌شان را ندارد

- استقرار روی زیرساخت زنده
- `git push` یا هر انتشار بیرونی
- پرداخت واقعی یا ارسال پیامک واقعی به یک فرد
- واردکردن تعرفه، حساب یا پروانه ساختگی به‌جای مقدار واقعی

هر کدام از این‌ها تصمیم و اجازه جداگانه لازم دارد.

## ۹. فاز ۲ — آنچه به این Runbook اضافه شد

### ۹.۱ مهاجرت و Seed

`npm run db:migrate` اکنون **۳۰ مهاجرت** اعمال می‌کند (۰۰۰۰ تا ۰۰۲۹). `npm run db:seed` علاوه بر تنظیمات و نژادهای پایه، **هشت Taxonomy نسخه‌دار** را تضمین می‌کند: گونه، گروه FCI، استان، شهر، تخصص دامپزشک، نوع مرکز، خدمت مرکز و امکانات مرکز. خروجی فرمان، نسخه هر Taxonomy و تعداد ورودی‌های افزوده‌شده در همان اجرا را چاپ می‌کند.

قاعده‌ها (DEC-0179):

- اجرای دوباره Seed فقط ورودی **غایب** را اضافه می‌کند؛ ورودی موجود هرگز به‌روزرسانی، تغییرنام یا دوباره فعال نمی‌شود. اگر اپراتور نام ورودی را عوض کرده یا خاموشش کرده، Seed آن را برنمی‌گرداند.
- افزودن ورودی تازه به یک Taxonomy، مهاجرت نمی‌خواهد: ردیف به کاتالوگ `src/db/seed/taxonomy.ts` اضافه و نسخه همان کاتالوگ یک واحد زیاد می‌شود.
- هیچ مهاجرت معکوسی وجود ندارد. همه مهاجرت‌ها افزایشی‌اند (تست `tests/domain/migrations.test.ts` این را قفل می‌کند)، پس نسخه قبلی کد روی Schema جدید کار می‌کند. برای بازگشت واقعی داده، مسیر امن همان بازگرداندن Snapshot است.

### ۹.۲ بررسی سلامت

`GET /api/health` علاوه بر دسترسی پایگاه‌داده، تعداد مهاجرت‌های اعمال‌شده، کلیدهای تعیین‌نشده و وضعیت هر Adapter، اکنون **نسل هر Taxonomy** را هم برمی‌گرداند. وضعیت `degraded` یعنی سامانه اجرا می‌شود ولی مقدار واقعی یا سرویس واقعی کم دارد؛ این پاسخ صادقانه است، نه خطا.

### ۹.۳ اجرای تست‌ها

```bash
npx tsc --noEmit
node --test --test-concurrency=4 "tests/domain/*.test.ts" "tests/config/*.test.ts" "tests/ui/*.test.ts"
node --test --test-concurrency=4 "tests/db/*.test.ts"
npm run build && node tools/browser-tests.mjs
```

`npm test` به‌صورت یکجا روی ویندوز با `spawn UNKNOWN` (errno ‎-4094) می‌افتد: اجراکننده برای هر فایل یک فرایند می‌سازد و ~۷۰ فایل همزمان منابع فرایند را تمام می‌کند. دو گروه بالا همان پوشش را می‌دهند.

`tools/browser-tests.mjs` **build نمی‌کند**؛ به `.next` موجود تکیه دارد. پس بعد از هر تغییر کد برنامه، اول `npm run build`.

### ۹.۴ عیب‌یابی یک شکست مرورگر

```bash
KEEP_BROWSER_DB=1 node tools/browser-tests.mjs tests/browser/<suite>.test.ts
```

پایگاه‌داده و فایل‌های خصوصی آن اجرا حذف نمی‌شوند و نامشان چاپ می‌شود، تا بتوان مستقیم از داده پرسید (`audit_event` معمولاً خود جواب را دارد). بدون این پرچم، هر اجرا پایگاه‌داده‌اش را حذف می‌کند — که پیش‌فرض درست است، وگرنه اجرای بعدی روی بازمانده اجرا می‌شود.
