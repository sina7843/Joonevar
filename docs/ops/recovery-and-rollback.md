# بازیابی و بازگشت — فاز ۲.۵

مطابق §۱۲ (PROMPT-016). این سند می‌گوید اگر ارتقا بد پیش برود چه کاری، با چه ابزاری و به چه ترتیبی انجام می‌شود.

دو واقعیت که همه چیز بر آن‌ها استوار است:

1. **مهاجرت‌ها به عقب برنمی‌گردند.** در این مخزن هیچ مهاجرت `down` وجود ندارد و عمداً هم نوشته نشده: مهاجرت‌ها `drop`/`rename` ندارند و افزودنی‌اند، پس راه بازگشتِ درست «اجرای معکوس» نیست، «بازگرداندن snapshot» است.
2. **پایگاه‌داده و فایل خصوصی یک واحدند.** سطر به فایل اشاره می‌کند؛ بازگرداندن یکی بدون دیگری یعنی رکوردی که سندش نیست یا فایلی که کسی به آن نمی‌رسد. `tools/backup.mjs` هر دو را در یک snapshot با manifest و digest می‌گیرد.

---

## پیش از هر ارتقا

```bash
# ۱. snapshot کامل (پایگاه‌داده + فایل خصوصی + manifest)
node tools/backup.mjs --out backups

# ۲. تمرین ارتقا روی یک پایگاه‌داده یکبارمصرف با داده نماینده
node tools/upgrade-check.mjs
```

`upgrade-check` مهاجرت‌های تا فاز ۲ را می‌زند، رکوردهای نماینده (حساب، پروفایل، حیوان، عضویت مادام‌العمر، انجمن و کلاب منتشرشده، هم‌مدیر، پرداخت قدیمی) می‌نویسد، سپس مهاجرت‌های فاز ۲.۵ را اعمال می‌کند و **قول‌های فاز** را روی همان داده بررسی می‌کند: عضویت مادام‌العمر مادام‌العمر می‌ماند و تاریخ انقضای ساختگی نمی‌گیرد، رکورد منتشرشده ACTIVE می‌شود ولی تأییدکننده اختراع نمی‌شود، هم‌مدیر موجود ADMIN می‌شود، و قلم پرداخت قدیمی همچنان می‌گوید قیمتش از تنظیم آمده.

آخرین اجرا: **۱۸/۱۸ بررسی پاس** روی ۸ مهاجرت فاز ۲.۵ (`0033`–`0040`).

## اجرای ارتقا

```bash
npm ci
npm run typecheck
npm run build
DATABASE_URL=... npm run db:migrate
DATABASE_URL=... npm run db:seed     # فقط چیزهای غایب را اضافه می‌کند
```

`db:seed` هرگز چیزی را که اپراتور تغییر داده برنمی‌گرداند: تنظیم دست‌خورده، دسته تغییرنام‌داده یا غیرفعال‌شده، و ورودی taxonomy حذف‌شده دست نمی‌خورند.

**نشانه‌های سلامت پس از ارتقا**

| بررسی | انتظار |
|---|---|
| `select count(*) from drizzle.__drizzle_migrations` | برابر تعداد فایل‌های `src/db/migrations/*.sql` |
| `/api/health` | پاسخ می‌دهد |
| صفحه `/admin` | داده‌های مدیریتی ثبت‌نشده را فهرست می‌کند |
| `/admin/notifications` | وضعیت صف؛ کانال پیامک خاموش است مگر روشن شده باشد |

## اگر ارتقا شکست بخورد

ترتیب کار، از کم‌هزینه به پرهزینه:

**۱. مهاجرت نیمه‌کاره.** هر فایل مهاجرت در یک تراکنش اجرا می‌شود؛ شکست یعنی آن فایل اصلاً اعمال نشده. علت را رفع کنید و `db:migrate` را دوباره بزنید — اجرای دوباره no-op است برای آنچه قبلاً ثبت شده.

**۲. مهاجرت اعمال شد ولی رفتار غلط است.** اگر نقص در کد است نه در schema (حالت معمول، چون مهاجرت‌ها افزودنی‌اند)، **کد را به کامیت قبلی برگردانید و پایگاه‌داده را دست نزنید**. ستون تازه‌ای که کد قدیمی نمی‌شناسد ضرری ندارد؛ جدول تازه خالی می‌ماند.

**۳. داده آسیب دیده است.** snapshot را برگردانید:

```bash
node tools/restore.mjs --in backups/<snapshot>
```

بازگرداندن، هر دو نیمه را با هم برمی‌گرداند و digest فایل‌ها را با manifest می‌سنجد. پس از آن، کد را به همان کامیتی برگردانید که snapshot با آن گرفته شده بود.

**۴. تنها یک جریان خراب است.** لازم نیست کل سامانه برگردد. مسیرهای فاز ۲.۵ کلید عملیاتی خودشان را دارند و بستن آن‌ها داده‌ای را از بین نمی‌برد:

| برای بستن | کلید | مقدار |
|---|---|---|
| پیامک بیرون‌رونده | `notifications.sms_enabled` | `OFF` |
| فروش دوره پروانه | `vet_licence.activation_toman` / `renewal_toman` | خالی |
| فروش دوره معتمد | `trusted_vet.activation_toman` / `renewal_toman` | خالی |
| درخواست معتمد | `guide_text.trusted_vet_terms` | خالی |
| پرداخت/درگاه | `integration.payment.mode` | `MOCK_AUTO` یا خالی‌کردن provider |

تنظیم بدون مقدار یعنی مسیر وابسته **بسته** است، نه اینکه با عدد صفر باز بماند. این همان رفتاری است که همه‌جا تست شده.

## آنچه بازگردانده نمی‌شود

- **رویدادهای audit.** جدول فقط افزودنی است و trigger پایگاه‌داده به‌روزرسانی و حذف را رد می‌کند. بازگرداندن snapshot، audit را هم به همان لحظه برمی‌گرداند؛ ویرایش انتخابی ممکن نیست و نباید باشد.
- **پیام‌های ارسال‌شده.** سطر تحویل SENT نشان می‌دهد چه چیزی و با کدام نسخه متن رفته است. بازگرداندن پایگاه‌داده پیام را پس نمی‌گیرد.
- **پرداخت تأییدشده.** بازگرداندن پایگاه‌داده پول را برنمی‌گرداند. اگر snapshot به پیش از یک پرداخت تأییدشده برگردد، آن پرداخت در سامانه ناپدید می‌شود ولی در درگاه هست؛ تطبیق آن کار انسانی انجمن است و باید با گزارش درگاه انجام شود.

---

## تمرین توصیه‌شده پیش از تحویل

1. یک کپی از پایگاه‌داده تولیدی بگیرید.
2. `TEST_DATABASE_URL` را به آن کپی بدهید و `node tools/upgrade-check.mjs --keep` را بزنید.
3. پایگاه‌داده باقی‌مانده را با چشم ببینید: عضویت‌های قدیمی، کلاب‌های منتشرشده و پرداخت‌های پیشین.
4. همان کپی را با `tools/restore.mjs` از snapshot برگردانید تا مسیر بازگشت هم یک‌بار واقعاً اجرا شده باشد.

این تمرین هنوز روی داده تولیدی انجام نشده است — داده تولیدی در دسترس این محیط نیست.
